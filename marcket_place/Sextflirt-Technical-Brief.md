## 1. What This System Actually Does
 
Sextflirt is a web platform where registered users create a profile, verify an age-gated identity, and post photos or short videos tagged with interests. Other users browse, like/dislike, comment, and can "love" a profile. Posts and profiles are also organized around a "social medium" concept — each profile links out to that user's Snapchat/Kik-style account (the app stores an external app username per profile and generates a QR code linking to it), so the platform functions as a content/discovery layer that drives traffic to those external social accounts.
 
There's also a secondary content vertical: a "pornstar" directory with its own posts/pages, plus a blog and static "document" (legal/info) pages, apparently used for SEO and content marketing around the platform's core theme.
 
Two audiences use it:
- **End users** — sign up, verify age/email, post content, browse/filter others by gender, tag, or platform, and react to posts.
- **Site admins/moderators** — a separate `/master` admin panel to manage users, posts, tags, interests, countries, ad placements, blog content, ID verification approvals, reports/moderation, and site-wide settings (rate limits, page copy, disclaimers).
This is an adult/dating-adjacent content platform, so age verification, content moderation, and email-quality controls (see Sections 7–8) are core to what was built, not incidental.
 
## 2. Architecture
 
- **Pattern:** Laravel monolith (MVC + Blade views), single-tenant, no SPA/API-first split. There is a thin `routes/api.php` but it's only used for a webhook callback and an authenticated `/user` endpoint — not a general API surface.
- **Three route groups**, each with its own middleware stack, defined centrally in [`RouteServiceProvider::boot()`](app/Providers/RouteServiceProvider.php):
  - `routes/web.php` — public + authenticated user-facing site (`web` middleware group).
  - `routes/admin.php` — mounted under `/master`, gated by a custom `admin` middleware group (`web` + `auth` + [`AdminMiddleware`](app/Http/Middleware/AdminMiddleware.php)).
  - `routes/api.php` — mounted under `/api`, `api` middleware group (throttle + bindings only).
- **No repository layer, no FormRequest classes, no Policy classes.** Validation and authorization live directly in controllers (`$request->validate([...])` inline, `auth()->user()->isAdmin()` checks). This is a deliberate simplicity choice for a monolith of this size, not an oversight — but it means authorization logic is duplicated per-controller rather than centralized.
- **Service/helper layer:** small, purpose-built classes under `app/Support/` (`Bunny`, `Coconut`, `Avatar`, `TinifyService`, `QrCode`, `Settings`) wrapping third-party integrations and file-processing routines. `app/Actions/Fortify/*` holds Fortify's pluggable auth actions (create/update user, password reset).
- **Polymorphic relations:** `Reaction` (likes/dislikes) is `morphMany`/`morphTo`-style via `reactionable_id` + `reactionable_type`, currently only used against `Post`, via a shared `Likeable` trait ([`app/Models/Helper/Likeable.php`](app/Models/Helper/Likeable.php)) that both `User` and `Post` use. The schema was migrated from a hard `post_id` foreign key to the polymorphic pair in [`2022_12_07_034503_add_reactionable_id_and_reactionable_type_column_on_reactions_table.php`](database/migrations/2022_12_07_034503_add_reactionable_id_and_reactionable_type_column_on_reactions_table.php) — evidence of a deliberate refactor to generalize reactions beyond posts, done as a proper migration (dropped FK/unique, renamed column, re-added a composite unique on `(reactionable_type, reactionable_id, user_id)`).
- **No multi-tenancy.** Single database, single site. There is an `AdminMiddleware` role gate (`users.type === 1`) but no per-tenant data isolation, no tenant column anywhere in the schema.
- **DB design notes:**
  - `deleted_at` (soft-delete column) was added to `users` in [`2021_07_06_140001_modify_users_table.php`](database/migrations/2021_07_06_140001_modify_users_table.php) via `softDeletesTz()`, but the `User` model does **not** use Laravel's `SoftDeletes` trait. So the column exists in the schema but Eloquent performs hard deletes (`$user->delete()` in [`Admin\UserController::destroy()`](app/Http/Controllers/Admin/UserController.php) permanently removes the row). This looks like an abandoned soft-delete plan — flag as "unclear, needs my input" on whether that's intentional.
  - The original `users` table (first migration) has fields like `karma`, `statut`, `trending`, `serp_index`, an `app` enum limited to `snapchat`/`kik` — reads like it was adapted from an existing/reference schema, then reshaped over several follow-up migrations (`2021_07_06_140001_modify_users_table.php` and later) into the current shape: dropped dead columns, added unsigned FKs, unique constraints, 2FA columns (unused — no 2FA UI is wired up, see Section 7), soft-delete column, renamed fields to `age`/`username`/`gender`/`avatar`/`social_medium_id`.
  - **Data quality artifact:** in that same modify migration, several `renameColumn()` calls target names with a trailing space — `'age '`, `'username '`, `'gender '`, `'avatar '`, `'created_at '` (see the file directly). Whether the live production columns actually carry a trailing space in their name is unverifiable from code alone — worth checking against the real schema before claiming this as a defect anywhere public-facing.
  - Composite index added on `users(gender, has_post, created_at)` ([`2022_11_13_...`](database/migrations/2022_11_13_122817_add_gender_has_post_created_at_index_on_users_table.php)) specifically to support the gender/has-post filtered, latest-first browse queries used on the home feed — an index added in response to an actual query pattern, not a blanket index-everything approach.
  - `posts.code` is the route key (`getRouteKeyName()` returns `code`), a random 7-char string, not the numeric ID — avoids exposing sequential IDs in URLs.
  - `Story.images` is cast to a PHP object and stores an array of per-image status/file entries (a JSON column used as a small embedded document rather than a normalized child table) — reasonable for a bounded, order-sensitive list capped at `MAX_NUMBER_OF_IMAGE = 10`.
## 3. Notable Technical Decisions
 
- **Gmail alias/dot canonicalization on email uniqueness.** Both registration ([`CreateNewUser::validate()`](app/Actions/Fortify/CreateNewUser.php)) and the ban flow ([`User::ban()`](app/Models/User.php)) normalize Gmail addresses by stripping `+tag` and dots before the `@` and re-appending `@gmail.com`. This closes the well-known Gmail multi-account trick (`user+1@gmail.com`, `u.ser@gmail.com` all resolve to the same inbox) for both duplicate-signup prevention and for making a ban actually stick. This is the kind of correctness detail that isn't obvious unless you've already been burned by users working around a naive unique-email check.
- **Dynamic, admin-configurable rate limits.** `post-limit` and `like-limit` rate limiters ([`RouteServiceProvider::configureRateLimiting()`](app/Providers/RouteServiceProvider.php)) pull their per-day caps from a cached `Setting` lookup rather than being hardcoded, and differentiate verified vs. non-verified users for posting. The post-limit limiter also renders a custom `errors.limit` view instead of a bare 429 — a considered UX decision, not just "add throttle middleware."
- **Content moderation via a keyword blacklist**, applied to both post captions ([`PostController::validateCaption()`](app/Http/Controllers/PostController.php)) and registration bios ([`CreateNewUser::bioAndFingerprintValidate()`](app/Actions/Fortify/CreateNewUser.php)) — a `BlacklistKeyword` lookup rather than free-text moderation, cheap and predictable.
- **Async video pipeline with a webhook completion callback.** Video uploads go to S3 as a temp object, get handed to Coconut.co for transcoding (mp4/webm/thumbnail outputs), and the post is created in an unpublished state (`status = 0`) until Coconut's webhook (`POST /api/my-share`) marks it published and deletes the temp S3 file. This is a legitimate async-processing pattern for a task that can't complete inline — see Section 4/7 for the gap in how that webhook is secured.
- **Route-model binding by human-readable key, not ID**, throughout (`{user:username}`, `{blog:slug}`, posts by `code`, settings by `field_name`). Consistent choice across the codebase, not just one controller.
- **Anti-pattern worth flagging:** [`PostController::storeVideo()`](app/Http/Controllers/PostController.php) wraps `DB::beginTransaction()`/`DB::commit()` around an S3 upload and a Coconut API call — i.e., a DB transaction held open across two slow external network calls, with no `try/catch`/`rollBack()` on failure. If either external call throws, the transaction is abandoned rather than explicitly rolled back. This is a correctness/robustness gap, not a security issue.
- **Legacy/commented-out fingerprint dedup.** `bioAndFingerprintValidate()` still contains a commented-out fingerprint-based duplicate-account check (`header('Location: ...); exit();` pattern, bypassing Laravel's response cycle entirely rather than returning a redirect response). Matches the recent commit `f54b9c3 fingerprint validation removed` — this was a deliberate rollback of a former anti-fraud control, not dead code no one noticed. Worth asking why it was removed before presenting this as a "fraud prevention" feature.

## 5. Performance & Scale Considerations
 
- **Caching:** Minimal and narrow — only [`app/Support/Settings.php`](app/Support/Settings.php) uses `Cache::rememberForever()`, for admin-configurable settings (rate limit values, page copy). No general query caching, no view caching, no object caching layer for feed/post queries.
- **Queue:** No queue jobs exist in the codebase at all (no `app/Jobs` directory, nothing implementing `ShouldQueue`). `.env.example` sets `QUEUE_CONNECTION=sync`. Email sending, avatar processing, and everything else runs inline in the request. The one genuinely async operation (video transcoding) is offloaded to a third-party API (Coconut) with a webhook callback, not to a local queue.
- **Scheduler:** [`app/Console/Kernel.php`](app/Console/Kernel.php) has its `schedule()` method essentially empty — a sitemap-generation command exists (`app/Console/Commands/GenerateSitemap.php`) but its scheduled-task line is commented out. Whether sitemap regeneration runs via an external cron (server crontab, not Laravel's scheduler) is unclear from code alone.
- **N+1 avoidance:** Deliberate and consistent in the hot paths. `Post::scopeLoadRelation()` eager-loads `tags`, a trimmed `user` column set, `user.country`, and `user.socialMedium` in one call. The main feed query in [`PostController::getPosts()`](app/Http/Controllers/PostController.php) batches reaction counts and the current user's own reaction in two grouped queries against the whole paginated result set, rather than querying per-post — a specific, intentional fix for what would otherwise be an N+1 on every feed render.
- **Indexing:** targeted, not blanket — see the composite `(gender, has_post, created_at)` index in Section 2, added to match an actual filtered/sorted query shape.
- **Overall assessment:** built for a moderate-traffic content site, not for extreme scale. No read replicas, no queue-based decoupling of write-side work (image processing, email, CDN purge all happen synchronously in the request/response cycle), no cache layer beyond a small settings cache. That's a reasonable choice for the traffic tier this looks like it targets, but it is not evidence of "designed for heavy load" — it's evidence of a pragmatic, request-synchronous build.

## 7. Security Posture
 
- **AuthN:** Laravel Fortify (session-based, cookie auth), with 2FA rate limiters configured in [`FortifyServiceProvider`](app/Providers/FortifyServiceProvider.php) — but there's no visible UI wiring for 2FA (`app/Actions/Fortify` has no two-factor enable/confirm action beyond what Fortify ships, and no 2FA setting is exposed in the profile views checked). The `users` table does carry `two_factor_secret`/`two_factor_recovery_codes` columns from the schema migration, so 2FA may be partially scaffolded but not completed — flag as "unclear, needs my input."
- **AuthZ:** Single boolean admin flag (`users.type === 1`, checked via `User::isAdmin()`), enforced by a custom `AdminMiddleware` at the route-group level (`web` + `auth` + `AdminMiddleware`, correctly ordered so `auth()->user()` is never null when `isAdmin()` runs). No granular roles/permissions — it's admin-or-not.
- **Input validation:** Inline `$request->validate([...])` per controller action (no FormRequest classes), consistently applied — registration, post creation, admin CRUD, etc. all validate types, existence (`exists:table,column`), uniqueness, and string length.
- **Email-quality controls specific to this domain:** `IsEmailWhiteListed` (registration only accepts allow-listed email domains), `BannedEmail` (blocks previously-banned addresses, including the Gmail-canonicalized form), age gate `min:18, max:78` at public registration.
- **Inconsistency worth flagging:** the **admin** user-edit form's age validation ([`Admin\UserController::validateData()`](app/Http/Controllers/Admin/UserController.php)) allows `age` as low as **15** (`'min:15', 'max:255'`), while public self-registration enforces **18+**. For an adult-content platform, that gap between the admin-editable minimum and the public minimum is worth a direct conversation with the client/stakeholder before this is described anywhere as "age-verified" — it may be intentional (e.g., admin correcting a genuine data entry error) or it may be an oversight. Don't guess; ask.
- **Genuine vulnerability to flag privately (not fixed, just flagged):** `routes/api.php`'s `POST /api/my-share` endpoint (the Coconut transcoding webhook) has **no authentication, no signature verification, and no payload validation** — only the blanket `api` middleware group (`throttle:api` + route-model binding). Anyone who can guess or observe a `job_id`/`coconut_id` value can:
  1. Force-publish any pending video post (`Post::published()`), bypassing whatever review gate that unpublished state was meant to provide, and
  2. Trigger an S3 delete of an attacker-supplied `temp_file` path (`Storage::disk('s3')->delete($request->temp_file)`) with no validation that it belongs to the request's own upload — a potential arbitrary-object-delete on that bucket, depending on IAM permissions on the credentials in use.
  It also has no null-check — if `job_id` doesn't match a post, `->published()` is called on `null` and the request fails with an unhandled error, which is a robustness bug on top of the security gap.
- **IP-spoofing surface:** [`GetGeoCityFromIp::getIp()`](app/Http/Middleware/GetGeoCityFromIp.php) trusts client-supplied `X-Forwarded-For`/`X-Forwarded`/`Client-IP` headers directly, with no check against a configured trusted-proxy list (`TrustProxies` middleware exists separately but this method doesn't defer to it). Impact here is low — the value only drives a cosmetic "near you" city/flag — but if that IP value is ever reused for anything security-sensitive (rate limiting, geofencing, fraud signals), it would be spoofable.
- **CSRF:** Standard Laravel `VerifyCsrfToken` middleware is active on the `web` group; nothing excluded from it that I found.
- **Secrets:** No hardcoded credentials found in the app code — all third-party keys are `env()`-sourced in `config/services.php`. (`.env` itself is git-ignored per `.gitignore`; not present in the repo as read.)
## 8. Complexity & Difficulty Assessment
 
What was genuinely non-trivial here:
- **The async video pipeline** (upload → S3 temp → Coconut transcode → webhook → publish + cleanup) touches three external systems and has to handle partial completion correctly (a post exists in an unpublished state while transcoding is in flight). Getting this right — including cleaning up temp storage — is a real distributed-systems-lite problem, even at small scale. (That said, the transaction-handling and webhook-auth gaps noted above show where it's incomplete.)
- **The reaction/like system's evolution** from a simple `post_id` FK to a proper polymorphic relation via an actual reversible migration, without breaking the existing `Likeable` trait consumers — that's the kind of refactor a less experienced developer typically avoids (or does by dropping and recreating data) rather than doing as a clean schema migration.
- **Framework version migrations while live** — the git history shows sequential upgrades (Laravel 8 → 9 → 10, see commits `4dc1948` and `5531f1a`) on an active codebase, which requires dealing with breaking changes across major versions without a large test suite to catch regressions (see Section 6 — this was done with essentially no automated safety net, which raises the real difficulty of doing it without introducing regressions).
- **Domain-specific dedup/anti-abuse logic** (Gmail canonicalization, email whitelist/blacklist, keyword-based content moderation, configurable per-day post/vote limits) — none of this is hard in isolation, but stitching several independent anti-abuse mechanisms together consistently (applied at both registration and ban time) is the kind of detail work that's easy to under-scope.
What a less experienced developer would likely have gotten wrong:
- Skipping eager-loading on the feed query (the N+1 avoidance in `getPosts()`/`scopeLoadRelation()` is not accidental).
- Not indexing for the actual filtered/sorted feed shape (the composite index was clearly added in response to a real query, not preemptively).
- Trusting `X-Forwarded-For` blindly for something more consequential than a cosmetic city label (this codebase did trust it blindly, but only for a low-stakes value — a beginner might make the same mistake somewhere higher-stakes).
- Leaving the webhook endpoint unauthenticated is exactly the kind of gap that's easy to miss at any experience level when a third-party service's webhook contract doesn't hand you an obvious signature scheme (Coconut's webhook payloads aren't signed in this integration) — worth being honest that this wasn't caught, not worth over-crediting either way.
